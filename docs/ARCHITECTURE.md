# OpsIntel — Architecture

**Problem.** Operations teams receive CSV exports full of duplicates, mixed date formats,
inconsistent spellings and missing values. Cleaning them by hand is slow and untraceable.

**Solution.** Upload a CSV → the original is stored in S3 → a backend pipeline validates,
cleans and de-duplicates every row → clean records land in RDS MySQL → a web app shows a
dashboard, automatic insights, searchable records and a data-quality report that accounts for
every row received.

## Why each AWS service exists

| Service | Purpose | Why not the alternative |
|---|---|---|
| **S3** | Immutable original of every upload + cleaned and rejected outputs. Traceability and re-processing. | EC2 disk is lost with the instance and can't be shared. |
| **RDS MySQL** | Relational store for filtering, search, aggregation and dashboard queries; managed backups and patching. | DynamoDB is weak at ad-hoc aggregations; self-hosted MySQL means managing backups ourselves. |
| **EC2** | Runs the web app, API and processing worker. | Lambda: needs VPC + pandas layer + 15-min limit; more moving parts for a one-day build. Pipeline code is isolated so it can move to Lambda/Glue later. |
| **IAM role** | Gives EC2 access to exactly one bucket's three prefixes and this app's SSM parameters. No access keys anywhere. | Access keys in a `.env` file can leak. |
| **SSM Parameter Store** | Stores DB passwords as encrypted SecureStrings; the app reads them at startup. Also Session Manager / Run Command for admin without SSH. | Secrets Manager adds cost; hard-coding is unacceptable. |
| **VPC security groups** | Web port open; database reachable only from the app server's security group. | Public DB or SSH exposed to the internet. |

## Data model (RDS)

| Table | Purpose | Key points |
|---|---|---|
| `uploads` | One row per file: lineage (S3 keys), status/stage, counts, success rate, quality score | `file_hash` UNIQUE blocks re-loading the same file |
| `orders` | Clean, typed, de-duplicated records + derived `revenue`, `order_month`, `sla_breached` | `order_id` PK stops duplicates across uploads; indexes on date, region+category, status, month |
| `rejected_rows` | Every refused row with all reasons, kind and original values | Nothing is silently dropped |
| `quality_issues` | Per-column issue counts | Feeds the quality matrix |

## Pipeline guarantees

* `total = valid + invalid + duplicates` for every upload.
* One database transaction per upload: either everything for that file is stored, or nothing.
* Failures are recorded as `FAILED` with a readable message; the raw file stays in S3 for retry.
* A single worker processes uploads in order, so two uploads never race on the same records.

## Security summary

* No credentials in code or git; passwords generated by AWS and stored only in SSM.
* App DB user has privileges on the `opsintel` schema only and must use TLS (`REQUIRE SSL`).
* RDS: private, encrypted, reachable only from the app security group.
* S3: Block Public Access, default encryption, versioning, policy denying non-TLS requests.
* EC2: IMDSv2 required, encrypted disk, no SSH port, service sandboxed by systemd.
* Web: strict Content-Security-Policy, `nosniff`, frame `DENY`, all user data rendered as text,
  SQL via bound parameters with whitelisted sort columns, rate limits in nginx.

## Scaling path

| Pressure | Next step |
|---|---|
| Bigger files | Browser → S3 presigned upload; chunked processing; AWS Glue/Spark for very large data |
| More uploads | SQS queue + multiple workers (or S3 event → Lambda), per-key upserts |
| More users | Auto Scaling group behind an ALB (HTTPS via ACM); RDS read replica for dashboards |
| More dataset types | Add a JSON profile in `app/profiles/` — validation and cleaning are profile-driven |
