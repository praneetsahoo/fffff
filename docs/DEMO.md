# OpsIntel — Demo script (about 6 minutes)

Before judging: open the site, check the top bar shows **Database connected** and **Amazon S3**
with green dots, and download `operations_orders_live_demo.csv` from the Upload page if it is not on the
demo laptop already.

The live site is pre-loaded with `operations_orders.csv` and `operations_orders_batch2.csv`, so the
dashboard is full from the first second. For the live upload in front of judges use
**`operations_orders_live_demo.csv`** (2,060 rows, never uploaded). Re-uploading either
pre-loaded file shows the duplicate-file protection.

## 1. The problem (30 s)
"Operations teams get CSV exports from many branches: duplicates, three date formats,
'Bombay' vs 'Mumbai', blank fields. Today someone fixes them by hand and nobody can say what
was changed. OpsIntel makes that automatic and auditable."

## 2. Upload (1 min) — Upload page
1. Drag `operations_orders_live_demo.csv` onto the drop zone.
2. Point at the steps as they light up: **stored → validated → saved → loaded → ready**.
3. Read the row-accounting bar: *"every row received is accounted for: loaded, rejected with a
   reason, or removed as a duplicate."* Then click **Open dashboard** — the numbers have grown.

## 3. Break it on purpose (45 s)
Upload `missing_columns.csv`, then `not_really_csv.csv` (both downloadable under
"Files that should be refused"). Each gets an instant, specific message and nothing is stored.
Upload `operations_orders.csv` again → "already uploaded" (duplicate-file protection).

## 4. Dashboard (1.5 min)
* KPI strip — revenue, orders, average order value, late deliveries: **all computed live with
  SQL from RDS**.
* "What changed" — the system found on its own that **East deliveries are getting late**
  (85% vs 8%) and **Electronics demand surged in September**.
* Show the late-deliveries chart (East in red above the tolerance line).
* Set Region = East → every number and chart updates.

## 5. Records (45 s)
Search `mumbai`, filter Category = Electronics, sort by Revenue, then **Export CSV** — exactly
the filtered rows.

## 6. Data quality report (1 min)
* Issues by column: red = problems found, blue = fixed automatically (e.g. 1,497 dates
  converted to one format).
* "Refused rows" tab: each row with its line number in the original file and every reason.
* Download the original (from S3), the cleaned file and the rejected file.

## 7. Architecture (30 s) — `docs/ARCHITECTURE.md`
Browser → nginx → FastAPI on EC2 → raw file to S3 → pipeline → one transaction into private
RDS. IAM role (no keys), passwords in SSM, DB reachable only from the app.

## Likely judge questions
| Question | Answer |
|---|---|
| Why store in S3 before processing? | Immutable original for audit and re-processing; decouples ingestion from processing. |
| What if the DB fails mid-load? | One transaction per upload → rollback, status FAILED with message, raw file kept, Retry button. |
| How are duplicates handled? | File hash (same file), order_id primary key (same record across uploads), exact-row check within a file. |
| Success rate vs quality score? | Success = rows we could use (93%). Quality = rows that arrived perfect (19%). The gap is what the pipeline repaired. |
| How does it scale? | S3 presigned uploads, SQS + workers or Lambda/Glue, ALB + Auto Scaling, RDS read replica. |
| Where are the passwords? | Generated by AWS, stored only in SSM SecureString, read by the instance role at runtime. |
| Can the DB be reached from the internet? | No: private RDS, security group allows 3306 only from the app server's security group. |
| Why one worker thread? | Single writer means no race between uploads; the next step is a queue with multiple workers. |
